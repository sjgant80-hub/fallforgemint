◊ Re-run it in CI — a neutral machine, in the open

    
A scorecard proves nobody edited the numbers. The re-run rail goes one step further: a clean GitHub runner rebuilds the model from its recipe, runs every held-out example through the base model and the minted one again, and checks the result against the signed record. If the scorecard says a CI run minted it, the rail looks that run up on GitHub and checks it made this exact scorecard, so a forgery that borrows a genuine run's link fails. Anyone can run it. No account with us, and no need to trust us.

    
    
      
  1. Get the bundle. After Prove it, download the signed scorecard, then Download re-run bundle. It holds the receipt, the recipe and the held-out rows.
    2. 
      
  2. Make your own copy of the runner. Open fallforgemint-rerun, press Use this template, and add your bundle to it (e.g. bundle.json). Your copy calls the rail's own workflow here, so the code that judges your bundle is the gated code. Or fork fallforgemint itself, and enable workflows in the fork's Actions tab first.
    3. 
      
  3. Run it. Actions → rerun → Run workflow, with your bundle's path. It installs Ollama on the runner, rebuilds the model, re-runs the held-out set and grades it.
    4. 
      
  4. Send the run link. The run's summary shows the verdict, and its artifact holds a self-hashed attestation bound to that run's address. The link is the proof.
    5. 
    

    

      
REPRODUCED Same runtime and model digest. The hits match exactly.

      
AGREES A different runtime (your browser's model vs Ollama on the runner). The verdict holds.

      
TAMPERED A recorded number does not recompute, or the CI run the scorecard names did not make it. The job fails and nothing is re-run.

      
DID NOT REPRODUCE The record is intact but the result did not hold. The job fails.

    

    
Proven both ways, on real runs: the proof scorecard was minted on a GitHub runner (the mint run). Untouched, its link is BOUND — the run it names made this exact scorecard — and it is REPRODUCED: here, and from the template. One minted through the template binds too: run. Forged with care — the wrong answer rewritten, every hash recomputed, re-signed, the genuine run's link kept — every number recomputes, but the run it names made a different scorecard, so it is TAMPERED and the job fails: the failed run. The same forgery without the link is caught by re-running it, DID NOT REPRODUCE: run. An edited hit count is TAMPERED: run. The 90-day expiry path has not happened on a real run yet; the first proof artifact expires on 2026-12-27.

    
What it shows, and what it doesn't: every recorded number is recomputed from the bundle, and the held-out set is run again on that runner. A small model on a CPU is not bit-exact across chip types, so a borderline answer can flip between runners; the rail fails that record and shows you the row. GitHub keeps a run's upload for about 90 days; after that the rail can confirm only that the named run was the rail and was running when the scorecard was stamped, not that it made this exact one, and it says so. It does not attest the machine that made the original, and it says nothing about what the base model saw in its own training. A scorecard made in your browser is re-run on Ollama's build of the same model (qwen2.5:0.5b) — a different runtime and quantisation — so its test is AGREES, not an exact match.

    ◊ Risks, answered straight
    
    
    
      
    What if a small model isn't good enough for our job?
    Then the scorecard says TIES or LOSES, and you keep renting for that job. The shipped review-1b record in the Proof section shows exactly that: it beats its own base and loses to a bigger model, on the record.
    
      
    Is this real training?
    The mint on this page is few-shot tuning baked into a Modelfile — a real, owned, reproducible model, not weight fine-tuning. Weight-level tuning is part of the done-for-you service, where it helps.
    
      
    Could a scorecard be faked?
    Editing a number breaks its fingerprint and its signature — try it in the trace above. A careful forgery that recomputes every hash and re-signs is caught by the neutral re-run: the rail's proof runs show it failing on the CI run's link, and without the link, on re-execution.
    
      
    Were the test answers leaked into the model?
    The held-out answers are checked to be absent from the spec the model was given (hash-disjoint); for a few-shot model that spec is everything it was given. It says nothing about what the base model saw in its own pre-training, and the page says so.
    
      
    Will it give identical results on every machine?
    Not always, and the page says so: small models on CPUs are not bit-exact across chip types, so a borderline answer can flip. The rail fails that record and shows the row; the proof set holds out only rows that stay put.
    
      
    Can one machine take our volume?
    The own-vs-rent calculator works it out: from a measured answer time (the shipped review-1b record's) it shows how many calls a month one machine answers, one at a time, and how many machines your volume needs — put their cost in. Your job and hardware will differ, so time it on your own machine in step 4 of the roll-out, beside the current process.
    
      
    What if our job changes?
    Re-mint from new examples. The fingerprint changes with the Modelfile, so you always know exactly which model is running.
    
      
    Are we locked in?
    No. MIT licence, open formats, and it runs on Ollama, which is free.
    
      
    Can we use it for legal, tax, medical or financial decisions?
    No. Regulated work needs proper professional sign-off first. This is for the everyday, high-volume, unregulated work.

    The white paper
    
  
    Own the narrow model, and prove it with a test that can lose.
    
  
    
    
    Most business AI spend goes on renting a general model, by the token or by the seat, to do narrow jobs that repeat. FallForge Mint replaces one such job with a small model the business owns: a deterministic Modelfile built from the business's own examples, run locally, and judged on examples kept out of its spec by a grader no model controls. The result is a self-hashed, signed scorecard that is allowed to report a loss, and a re-run bundle that a neutral machine re-verifies and re-executes. The page you are reading runs the mutation-gated code that does all of this.
    

    
    1 · The problem
    
    
    A narrow job — triage, extraction, tagging, a templated reply — does not need a frontier model, but renting one is the default. Its cost rises with volume, every case leaves the building, and the evidence that it works is the vendor's benchmark, not your work. Owning a small model fixes the first two; the third needs a test you can trust without trusting whoever made it.
    

    
    2 · The method
    
    
    Mint. The task and worked examples become a spec, and the spec becomes an Ollama Modelfile, assembled deterministically and fingerprinted with SHA-256 — the same inputs always give the same bytes. Prove. Some examples are held back; the kernel checks that their answers are absent from the spec (hash-disjoint), runs the base model and the minted one on them, and grades both against the right answers with a deterministic grader. Record. The scores, the fingerprints and the hashes of the task and the evidence go into a canonical, self-hashed scorecard, signed with Ed25519; a score that disagrees with its hit counts is refused even if the hash is recomputed. Re-run. A bundle of the scorecard, the recipe and the held-out rows goes to a clean GitHub runner, which recomputes every number, checks that the CI run the scorecard names really made it, rebuilds the model with a pinned Ollama and runs the held-out set again.

    4 · The limits, stated straight
    
    
    The mint is few-shot tuning at the Modelfile level, not weight fine-tuning. Small models on CPUs are not bit-exact across chip types, so a borderline answer can flip between runners; the rail fails such a record rather than hiding it, and the repo keeps two fragile records with the runs that fail them. A browser-made scorecard carries a software key, so it proves the numbers are unedited, not who ran the test — the neutral re-run closes that gap. The held-out claim is narrow: the answers were not in the spec the model was given; it says nothing about the base model's pre-training.
    

    
    5 · Where the idea comes from

    Questions
    
  
    The things people ask.
    
  
    
    
    Do I really own the model?
    Yes. The mint produces a Modelfile — a plain text recipe — that you run on your own machine with a free tool called Ollama. The resulting model lives on your computer. There's no account, no per-token bill, and it keeps working with your internet off.
    
    
    Do I need to be technical?
    No. You paste your task and a few examples and press one button. To run the model yourself you install a free app and paste two lines we give you, step by step. If you'd rather not, we can set it up for you.
    
    
    Is my data safe?
    Yes. Everything on this page runs inside your own browser. Your task and examples are never sent to us or anyone else. The model you build runs on your machine.
    
    
    What's the catch with owning instead of renting?
    A small owned model is private and, at enough volume, cheaper — but it's specialised: built for the one job you gave it examples of, not a general chatbot. For a narrow, repetitive, high-volume task that's exactly what you want. The calculator above shows, honestly, when renting is actually the better deal.
    
    
    How do I know it's any good?
    Every minted node is measured against its starting point by a deterministic gate, and the result is written into a signed receipt that can — and sometimes does — say it lost. You can re-check that proof yourself in your browser, in the Proof section above.
    
    
    Who supplies it, and who supports it?
    AI Native Solutions — start at ai-nativesolutions.com. The code is MIT-licensed and keeps running without us. Support, service levels, warranty and liability for a deployment are agreed in that deployment's agreement.
    
    
    What does it cost?
    Building and downloading your Modelfile here is free — you own it, with no account and no per-token bill. If you'd rather we set it up and proved it for you, that's a service we offer too.
